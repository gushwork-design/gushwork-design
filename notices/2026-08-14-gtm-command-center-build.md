## Correction — two stacked cards in the frame are ONE component in two states

Caught by Utsav on review, 14 Aug 2026. **A design file has to draw both states side by side, so
the frame stacks them. The first build read that literally and rendered duplicates.**

| Frame shows | Actually is |
|---|---|
| Two Channel Breakdown cards (`236:32026`, `236:32226`) | **One table.** The toolbar checkboxes toggle **column groups** — `Spend & ROI` off is the first card, on is the second. The metric columns reflow 160/160/137.3 → 85.6 |
| Two Actual vs Target sections (`236:32496`, `236:32580`) | **One section.** The **`Show both`** toggle — off shows the tab-selected chart, on shows both |

Both are now single interactive components. `exports/dashboard/v2/data-table.md` already described
the column-group behaviour correctly ("the toolbar checkboxes toggle column-group visibility") —
the export was right and the build ignored it, which is the more useful lesson: **a stacked pair of
near-identical cards in a frame is a state matrix, not a layout.**

Behaviour where the design defines none, so nothing is invented beyond visibility:

- Any checkbox combination is allowed, including both off — that shows the channel column alone.
  No minimum-one-group constraint, because the design does not state one.
- Switching tabs while `Show both` is on changes the active tab but not what is displayed.
- **The tooltip colour differed between the two drawn states** (`Actual 1104` is `neutral/900` in
  the first, `red/500` in the second). As one component it can only be one: the semantic reading
  won — `red/500` when behind target, `green/500` when ahead, which is what the second state drew.

## Interactive pass — 14 Aug 2026

Requested: *"make this interactive… arrows beside table heading for sorting, info, dark mode,
light mode, dropdowns, paginations, all of it."*

**Dark mode is a token swap, not a filter.** A semantic alias layer (`--s-*` surfaces, `--b-*`
borders, `--t-*` text, `--d-*` data, `--tone-*` badges) is defined in `:root` from the light
tokens and re-pointed in `[data-theme="dark"]`. **Every dark value is measured** off frame
`236:33407` — including one I had recorded wrongly before: the **chrome border is `neutral/700`**,
while `neutral/800` is the *card* border. Also measured this pass: the dark **canvas is
`neutral/black`** (cards sit *lighter* than the canvas at `neutral/900`, and rows go back to black
inside them), the **inset panel is black on a `neutral/900` border**, and the **"Behind" badge is
`red/alpha-10` + `red/300`**. Persisted to `localStorage`; the light/dark control is the topbar
switcher from the frame.

| Behaviour | How it works | Source |
|---|---|---|
| **Sorting** | Every header cell is the control — click or Enter/Space cycles asc → desc → none. The `ArrowsDownUp` glyph swaps to `ArrowUp`/`ArrowDown`, and `aria-sort` carries the state. Numeric-aware (`$44.4K`, `3.67x`, `68%`, `681/706` all sort as numbers). The TOTAL row is pinned and never sorted | The arrows are drawn in the frame; the behaviour is implied, not specified |
| **Dropdowns** | Real menus: click or ArrowDown opens, arrows move, Escape closes, outside click dismisses. Wider than the trigger, right-aligned, **no selected checkmark** | Measured, `controls.md` — and the no-checkmark rule is one an earlier ruling had invented |
| **Pagination** | Prev/next page through 40 daily and 70 onboarding rows; page size 10/25/50/100 via its menu; status text updates; arrows disable at the ends using the measured `Outline`-disabled treatment (`neutral/250`) | Frame says "Page 1 of 4" / "1 of 7"; **no disabled arrow is drawn** — that gap is filled with the nearest measured value |
| **Quick Filter** | A real input, filtering live on domain / AE / channel, resetting to page 1 | The frame draws it as a select with placeholder text; an input is the honest control |
| **Tooltips** | 28 targets — the info rows, the `Day 18 of 30` question mark, "Choose columns", and every sort header. Hover **and** keyboard focus, flips above/below at the viewport edge | New; uses the v2 `tooltip` spec |
| **Sidebar collapse** | The chevron collapses to the **measured 64px** state — labels and group headers hidden, 32×32 icon cells, avatar-only footer, chevron flips to `CaretDoubleRight` | Measured `sidebar State=collapsed` |

Filter, sort and pagination share **one state object per table**, because wiring them
independently is what produces a sort that forgets the filter or a page that forgets the sort.

### Three bugs this pass introduced and measurement caught

1. **Light mode lost every section gap.** Inserting the alias block swept `--v-sect-gap` and
   `--v-slot-top` into the `[data-theme="dark"]` block, leaving them undefined in `:root` — so
   `margin-top: var(--v-sect-gap)` was invalid and computed **0px** in light mode. Visible only
   as slightly tighter spacing; caught by reading the computed value, not by looking.
2. **Tab switching lagged one click.** `render()` ran before the generic tab handler moved
   `.is-active`, so it read the previous tab. Now it reads the clicked element directly.
3. **Table rows had no dark surface.** `--s-row` was defined but `.trow` never consumed it, so
   rows stayed transparent instead of `neutral/black` on the `neutral/900` card.

And one **false alarm worth recording**: an immediate `getComputedStyle` read after flipping the
theme returned the *pre-transition* colour, because the alias layer animates
`background-color` over 120ms. It looked exactly like dark mode being broken. Verification has to
disable transitions before sampling — the same class of trap as `document.fonts.check()`.

### Verified

**Interaction: 30+ assertions, all passing** — 40/70/4 row sets; page 1→2→4 with next disabled at
the end and prev at the start; page size 25 → "Page 1 of 2"; sort asc/desc/none with correct
`aria-sort` and genuinely ordered values; sort-by menu ordering `annual ARR`; filter matching 14 of
70 then 0 with "Page 1 of 1"; TOTAL pinned after sorting; dark row black on a `neutral/900` card.
No console errors.

**Theme: 13 surfaces sampled in both modes** against the measured mapping — canvas, chrome,
topbar, card, header row, body row, inset, title, stat label, legend, badge, progress track,
nav-selected. All match.

⚠ **Sample data is now varied.** The frame repeats one identical daily row ten times; uniform rows
make sorting and filtering look broken, so the 40 daily and 70 onboarding rows are generated
deterministically with spread values. That makes the **`Sample data` badge question sharper, not
softer** — see *Worth a decision* below.

## Created — no library equivalent exists

### The chart — area plot, target line, today marker, tooltip, gauge ring
v2 has **no chart component**, and the v1 `Graph` is a different thing: `Bar` / `Line` /
`Grouped Bar` at 280/400/456 tall, single-series, with no target line and no gauge. The screens'
charts are cumulative area plots against a target. So this is **build-then-declare**.

Composed from tokens only:

| Part | Built from |
|---|---|
| Actual series | 2px `primary-500` stroke + a `primary-500` gradient area fading to 0 opacity |
| Target series | 2px `neutral-200`, `stroke-dasharray:6 6` |
| Gridlines | 1px `neutral-100`, `stroke-dasharray:3 4`, horizontal per tick + vertical per week |
| Today marker | 1px `neutral-700`, full plot height, with a `primary-500` dot on the series |
| Tooltip | white, 1px `neutral-100`, `radius/8`, `py-8 px-12`, `button-10` rows, `Shadows/S2` values |
| Gauge ring | 40×40 SVG, 3px track `neutral-100`, arc `red-500` / `green-500` by attainment, `button-10` label inside |
| Axes | `button-12` on `neutral-700`; the y column carries a 1px `neutral-900` axis rule |

**No new colour, radius, spacing or type value was introduced.**

⚠ **The plot geometry is traced, not data-bound.** The Figma curve is an illustration — there is
no dataset behind it. The readouts, tick values, week labels and tooltip figures are transcribed
exactly; the curve between the points is a smooth interpolation chosen to match the drawn shape.
Commented as such in the generator.

⚠ **A contradiction in the source, reproduced as-is:** the tooltip reads `Actual 1104 / Target
1235` while that chart's y-axis tops out at **340** and its readout says `260 of 340`. Two
different magnitudes in one chart. Faithful to the design; worth a look.

## Worth a decision

**1. There is no `Sample data` badge, and the numbers look real.**
The skill requires invented numbers to be visibly marked. You ruled *"the figma shared is the
truth source, follow it"*, and the badge is not in the design — so it is not in the build. The
consequence is that `$809K ARR Added`, `$808.98K` and the named AEs and domains in Onboardings
read as reporting. **A screenshot of this is indistinguishable from a real dashboard.** If it will
be seen outside a design review, either add the badge (and accept the divergence from Figma) or
swap the copy.

**2. The theme switcher is rendered but inert.**
Dark mode was out of scope, so the topbar toggle is drawn and does nothing — which is exactly the
"dead controls" trap in `build-rules.md`. It is commented in the source. Dark values are fully
measured in `exports/dashboard/v2/`, so wiring it is a small job rather than a design question.

Secondary:

- **The display type is unbound.** Every page, card and chart title uses a literal spec because
  no `--gw-text-*` matches (**R15**). Five `--dash-display-*` custom properties are declared at the
  top of the file, commented, so they are replaceable in one place when the tokens exist.
- **No hover / focus / disabled states beyond table rows.** Table rows hover; a focus ring is
  applied globally via `:focus-visible`. Buttons, selects and nav have no hover from v2 — the
  measured values are in `button.md`.
- **`channnel` is preserved as the header string** but rendered uppercase, matching the frame. The
  v2 export normalises this to `CHANNEL`; the build follows the frame because you ruled Figma the
  truth source. These two now disagree by one typo.

## Tokens

Every colour and Inter type style is **pulled by name from `foundation/tokens.css` at build
time** — the generator exits rather than falling back if a name is missing, and no hex is written
in it. That guard caught two real bugs:

1. The button type tokens are `--gw-text-button-10/12/14`, **not** `-med` suffixed as I first
   assumed — the build refused to generate.
2. Emitting only the listed tokens left `var(--gw-font-body)` undefined inside every
   `--gw-text-*` shorthand, which made the whole `font` declaration invalid and **silently
   dropped every size and line-height** to browser defaults. It rendered plausibly and was
   completely wrong. Fixed by resolving token references transitively; caught by measuring
   computed type, not by looking.

Colour — `white` `black` `neutral-25/50/100/200/300/400/500/600/700/800/900` ·
`green-25/400/500` · `yellow-25/400/500` · `red-25/50/400/500` · `primary-500` ·
`primary-alpha-10`
Radius — `radius-4/8/12/16/40` · Type — `body-10-sem` `body-12-med` `body-12-sem` `body-14-med`
`body-16-reg` `body-16-sem` `button-10` `button-12` `button-14`

**Values in use with no token** — gaps to raise, not inventions: the five display styles (R15);
the chart gradient stop opacities (.22 → 0); `stroke-dasharray` patterns; the 3px gauge ring
weight; the tooltip shadow, which uses the `Shadows/S2` values inline because a
`--gw-shadow-s2` reference in a generated file would need the shadow token block emitted too.
